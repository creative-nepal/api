Multi-sector billing SaaS — architecture

One account, many businesses, independent subscriptions per business, one shared wallet — the same relationship a Google Account has to Workspace, One, and Cloud billing.

Account owns → Business (mart / medical / restaurant) has → Subscription (own plan) funded by → Wallet (shared)
§01

Goals

  • One login works across every business the person owns, regardless of sector.
  • Each business subscribes to its own plan and features, independent of the others.
  • Adding a new sector means writing a new plugin, not forking the app.
  • Data for each business is fully isolated, even under the same account.
  • Billing consolidates into one invoice per account, itemized per business.

Non-goals (v1): multi-region data residency, white-labeling per business, offline-first POS sync. Called out explicitly so scope doesn't creep into the first build.

§02

High-level architecture

Deployment style: a modular monolith — internal modules strictly separated and talking through defined interfaces, not direct cross-module DB access. Simple to run now; any module can be extracted into its own service later without a rewrite.

§03

Core concepts & relationships

ConceptWhat it isScope
AccountThe human/owner identity. One login.Global
BusinessA mart, clinic, restaurant, etc. owned by an account. This is your tenant.Belongs to one account
MembershipLets an account invite staff to a business with a role (owner/manager/cashier).Links account ↔ business
SubscriptionA plan + billing cycle attached to one business.Belongs to one business
PlanA catalog entry per sector (e.g. Mart-Pro, Medical-Basic) defining price + feature flags.Global catalog
WalletPayment method shared across all businesses under the account.Belongs to one account
Platform invoiceWhat the business owes you — consolidated per account, itemized per business/subscription.Belongs to one account
Business invoiceThe mart's or clinic's own sales invoice to its customers — sector-specific.Belongs to one business

Keep platform billing (what the business owes you) and business billing (what the business's own customers owe it) as clearly separate concepts in code and schema — same billing engine internals, different entities.

§04

Module breakdown

Core modules — shared, sector-agnostic

  • Identity & Account — signup/login, OAuth, session issuance, profile.
  • Business & Membership — CRUD for businesses, invite/manage staff, role assignment.
  • Subscription & Entitlement — plan catalog, subscribe/upgrade/downgrade/cancel, hasFeature(business_id, key) — the single choke point every other module calls to check access.
  • Billing engine — invoice generation, tax calculation, PDF/receipt rendering, gateway integration, dunning, platform-level consolidated invoicing.
  • Notification module — email/SMS/push. Sector plugins publish events; this module doesn't know about sectors.

Sector plugin contract

Every sector plugin implements the same interface so the core never contains sector-specific branching:

interface SectorPlugin {
  sectorKey: string;                    // "mart" | "medical" | "restaurant"
  productSchemaExtension: JSONSchema;    // batch_no, expiry_date, etc.
  orderPipeline: OrderPipelineHooks;     // beforeCreate, onLineItemAdd, beforeCheckout
  invoiceLineBuilder: (order) => InvoiceLine[];
  defaultFeatureFlags: Record<string, boolean>;
  routes: Router;                        // mounted under /api/{sector}/*
}
Mart — barcode, weight pricing, stock transfer Medical — batch/expiry, Rx validation, regulatory export Restaurant — tables, KOT printing, split-bill

Adding a sector = a new plugin against this interface + a new plan catalog entry. Core, auth, subscription, and billing engine never change.

Indexing rule: every tenant-scoped table gets a composite index starting with business_id. Enforce the filter at the ORM/repository layer (a base repository class that injects it automatically) — not by convention — so a missing filter can't leak data across businesses.

§06

Multi-tenancy strategy

  • Shared schema, business_id column on every tenant table — cheapest to run and migrate; good default until compliance-driven customers require otherwise.
  • Row-Level Security (Postgres RLS) as a second line of defense: set app.current_business_id per request, add RLS policies so even a buggy query can't cross tenants.
  • Escalation path (only if needed): schema-per-tenant for large/enterprise businesses, or separate databases for regulated sectors — decide per-business, not platform-wide.
§07

Subscription & billing engine

Feature gating flow

  1. Request arrives with Authorization: Bearer <jwt> and X-Business-Id: <business_id>.
  2. Middleware verifies the account has a membership on that business.
  3. Any gated action calls entitlements.hasFeature(business_id, "kot.printing"), resolved via business → subscription → plan → feature_flags, cached in Redis, invalidated on plan change.

Billing cycle — async, queue/cron worker

  1. Nightly job finds subscriptions with current_period_end <= today.
  2. Charges the account's default payment method via the gateway.
  3. On success: extend period, mark active, append a line item to that month's platform_invoice.
  4. On failure: mark past_due, trigger dunning, then downgrade/suspend that business only — other businesses keep working.
  5. Monthly, a consolidation job rolls up all paid line items per account into one platform_invoice + PDF.

Business-level billing (the mart's own customer invoices) is generated synchronously at checkout using sector-specific invoiceLineBuilder and tax rules — kept in the shared core so pharmacy and restaurant tax rules don't fork the invoicing code itself.

§08

API design

REST, versioned. Sector-scoped routes require the X-Business-Id header and are mounted only if that business's plugin is active.

POST   /api/v1/auth/signup
POST   /api/v1/auth/login
GET    /api/v1/accounts/me
GET    /api/v1/accounts/me/businesses
POST   /api/v1/businesses
POST   /api/v1/businesses/:id/invite

GET    /api/v1/plans?sector=medical
POST   /api/v1/businesses/:id/subscription
DELETE /api/v1/businesses/:id/subscription

GET    /api/v1/accounts/me/wallet
POST   /api/v1/accounts/me/wallet/payment-methods
GET    /api/v1/accounts/me/invoices

-- sector-scoped, requires X-Business-Id header --
GET    /api/v1/products
POST   /api/v1/orders
POST   /api/v1/orders/:id/checkout
GET    /api/v1/mart/inventory/low-stock          -- mart-only, 404 for other sectors
GET    /api/v1/medical/batches/expiring          -- medical-only
POST   /api/v1/restaurant/tables/:id/kot          -- restaurant-only

Calling a mart route from a restaurant business returns 404, not 403 — plugin boundaries stay invisible to businesses that don't have them.

§09

Security & access control

  • AuthN: short-lived JWT access token + refresh token; OAuth optional at the account level.
  • AuthZ: role-based per business via memberships.role — evaluated per-request against the X-Business-Id in scope, never globally.
  • Payment data: never store card numbers — only gateway tokens.
  • Audit log: append-only table for subscription, plan, and staff role changes — needed for billing disputes and medical-sector compliance.

§11

Deployment

  • Single containerized app (API, worker, scheduler as separate processes) behind a load balancer — still one deployable unit.
  • Scale the API and worker tiers independently based on load.
  • Add Postgres read replicas once reporting/analytics queries start competing with transactional traffic.
§12

Migration path to microservices

Extract a module only when you hit a concrete wall — never preemptively:

  1. Billing engine — usually first. Different scaling profile (bursty, nightly jobs), already a clean boundary if module discipline held from day one.
  2. Notification module — easy second extraction, already purely event-driven.
  3. A specific sector plugin — only if that sector alone needs independent scaling (e.g. a very high-volume mart POS network).

Because the modular monolith forbids cross-module DB access and communicates through defined interfaces, each extraction is a deployment change, not a rewrite.

§13

Build order

  1. Identity & Account + Business & Membership — the "Google One" shell, no sector logic yet.
  2. Subscription & Entitlement + Plan catalog — with one dummy sector to prove flag-gating works.
  3. Billing engine — platform-level subscription billing first, simpler than business-level invoicing.
  4. First sector plugin end-to-end — pick your most-ready market, e.g. mart.
  5. Second sector plugin (medical or restaurant) — this proves the plugin boundary actually holds.
  6. Consolidated invoicing, staff roles, notifications.
