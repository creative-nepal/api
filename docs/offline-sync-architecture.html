Feature specification

Offline-first architecture — mobile & desktop

Mobile and desktop apps keep working when the internet drops mid-session. Products sync in the background; orders and invoices go straight to the server in real time, and only fall back to a local queue when the network genuinely isn't there.

Online — direct to server, real-time IRD push Offline — queued locally, retried every 15 min
§01

Offline-first principles

  • Losing internet mid-session must not interrupt work already in progress. If the app opened successfully with a valid session, a dropped connection afterward doesn't log the user out or block the screen they're on.
  • Products are cached locally so browsing the catalog, checking stock, and adding to cart work with zero network calls.
  • Orders and invoices try the server first (they need a real-time IRD/CBMS push) — they only fall back to a local queue when the request genuinely fails to reach the server.
  • Sync is never silent. The user can always see whether they're online, and whether anything is waiting to sync.
§02

Local data layer — SQLite on mobile & desktop

Both the mobile app and the desktop app carry a local SQLite database that mirrors just enough of the server's data to keep the app usable offline — it's a working cache and outbox, not a full replica.

-- local SQLite schema (mobile & desktop)

products               -- read cache, pulled from server
  id, business_id, name, category, unit_type, price,
  stock_qty, expiry_date, barcode, updated_at, synced_at

stock_movements_outbox -- local changes waiting to push (offline sales, adjustments)
  id (uuid, client-generated), product_id, delta_qty, reason,
  created_at, status  -- 'pending' | 'synced' | 'failed'

orders_outbox          -- orders that failed to reach the server
  id (uuid, client-generated), payload (json), created_at,
  retry_count, last_attempt_at, status

invoices_outbox        -- invoices generated offline, awaiting server confirmation + IRD push
  id (uuid, client-generated), order_ref, local_invoice_no,
  payload (json), created_at, retry_count, status

sync_log                -- audit trail of every sync attempt, for support/debugging
  id, entity_type, entity_id, direction, result, timestamp

Client-generated UUIDs on every outbox row — this is what makes retries safe. If a push times out but actually succeeded server-side, the retry carries the same UUID and the server just returns the existing record (idempotent), instead of creating a duplicate order.

§03

Auth continuity — app open vs. connection loss mid-session

Auth check happens once, at app open — not on every screen or action. After that, a dropped connection doesn't re-trigger a login requirement.

App opens

Reads the cached JWT (access + refresh token) from secure local storage. If it's not expired, the app opens straight into the dashboard — no network call required to get in.

Silent refresh, in the background

If online, the app quietly refreshes the token in the background so it stays valid. If this fails because there's no network, the app doesn't block — it just keeps using the still-valid cached token.

Internet drops mid-session

Nothing changes for the user. The cached token is still valid, product catalog is local, and the current screen keeps working. Only actions that require the server (like an order push) are affected — and those fall into the queue described below.

Token actually expires while offline

The app doesn't hard-lock the user out mid-shift. It allows continued use of already-cached data (browsing products, viewing queued orders) but blocks new server-bound actions until reconnect and re-auth — since a business-scoped write shouldn't happen on a token the server can no longer vouch for.

§04

Product sync — push/pull

Product data is read-heavy and low-conflict compared to orders, so it syncs on a simple pull-cache + delta-push model.

Product sync cycle

Same pull, triggered on demand
↓ merges into local SQLite ↓
Local product cache
Used for browsing, checkout, stock checks — works fully offline
↑ stock_movements_outbox ↑

Manual push button
Force-send pending changes now

Pull — server → device

  • Runs automatically every 15 minutes, plus a manual "Sync now" button in the UI for immediate refresh.
  • Delta sync: request is GET /products?business_id=..&updated_since=<last_synced_at> — only changed rows transfer, not the whole catalog every time.
  • New products, price changes, and stock corrections made by other devices/staff land here.

Push — device → server

  • Stock changes made while offline (a sale reduces stock locally) are recorded as movements (deltas), not overwritten absolute values — so two devices adjusting the same product offline don't clobber each other on sync; the server applies both deltas.
  • Pushed automatically every 15 minutes, and via the same manual button (push and pull run together on demand).
  • Server recomputes authoritative stock from all incoming movements and the next pull returns the corrected number to every device.

Why deltas, not snapshots: if Device A sells 2 units offline and Device B sells 3 units offline of the same product, pushing "stock = X" from each would overwrite one sale. Pushing "-2" and "-3" as movements lets the server apply both correctly regardless of order or timing.

§05

Orders & invoices — real-time first, offline fallback

Unlike products, orders and invoices are not queued by default — they attempt the server directly, synchronously, because an invoice needs the real-time IRD/CBMS push. The local queue only activates when that direct attempt actually fails.

StepOnlineOffline
Order createdSent directly to server, confirmed instantlySaved to orders_outbox locally, marked "pending sync"
Invoice generatedServer assigns official sequential number, pushes to CBMS in real timeSaved to invoices_outbox with a local reference; official numbering finalized once synced (see §06)
RetryN/A — already syncedAutomatic retry every 15 minutes, plus immediately on network reconnect
Staff visibilityShows as normal completed saleShows a clear "pending sync" badge until confirmed

Retry behavior

  1. Order/invoice creation is attempted against the server first, synchronously, with a short timeout.
  2. On failure (timeout, no network, server unreachable) → saved to the local outbox instantly, so the sale itself is never blocked or lost.
  3. A background worker retries everything in the outbox every 15 minutes, and also fires immediately when the device detects it's back online (network-state listener) — the 15-minute timer is the guaranteed backstop, reconnect detection is the fast path.
  4. Each retry is idempotent via the outbox row's client UUID, so a retry that partially succeeded earlier can't create a duplicate.
  5. Once synced, the outbox row is marked synced and the local record is reconciled with the server's authoritative response (official invoice number, IRD acknowledgment).
§06

Offline invoice numbering safety

The sequential, gapless invoice numbering rule from the compliance spec still applies even when a device is offline — this is the trickiest part of the whole sync design, worth calling out on its own.

The problem: the official sequence number must be assigned by the server (single source of truth, one counter per business per fiscal year). A device can't safely invent its own official number while offline — two offline devices could pick the same number, or numbers could go out of order once both sync.

Recommended pattern

  1. While online, each device periodically leases a small block of official invoice numbers from the server in advance (e.g. the next 30–50 numbers), stored locally.
  2. If the device goes offline, it issues real, valid, sequential invoice numbers from its leased block — checkout is never blocked, and the numbers are still officially reserved, not locally invented.
  3. If the leased block runs out while still offline, further sales get a local draft receipt (clearly marked "provisional, not yet an official invoice") queued in invoices_outbox; the official number is assigned the moment the device reconnects and syncs.
  4. On reconnect, unused numbers in a lease are reconciled — either carried forward or explicitly voided with a reason, so the register never shows an unexplained gap.

This is an addition to what was asked for, worth calling out explicitly: without number leasing, "save locally and retry" is safe for order data but risky for the official invoice number specifically. Leasing keeps every offline invoice fully compliant the moment it's printed, not just once it happens to sync.

§07

Sync/queue engine — internals

Background worker

A lightweight scheduler inside the app (mobile: WorkManager/BackgroundTasks; desktop: a local timer/daemon) fires every 15 minutes regardless of app state.

Network-state listener

Detects reconnect events and triggers an immediate sync pass rather than waiting for the next 15-minute tick — connectivity restored is a stronger signal than the clock.

Idempotency keys

Every outbox row's client-generated UUID is sent with the sync request; the server upserts rather than inserts blindly, so retries are always safe.

Exponential-ish safety

15-minute interval is the steady cadence; a failed sync doesn't hammer the server — it just waits for the next tick or the next reconnect event.

Conflict resolution

Products: server is always authoritative for absolute values; devices only ever send deltas. Orders/invoices: server-assigned IDs and numbers always win; local IDs are references, never final.

Full sync log

Every attempt (success or failure) is appended to sync_log — support staff can see exactly what synced, when, and what's still pending, per device.

§08

Sync status — what the user sees

  • Connection indicator — persistent small badge (online/offline) always visible, not buried in a settings screen.
  • Pending count — "3 orders, 1 invoice waiting to sync" visible at a glance when offline.
  • Manual "Sync now" button — for both product pull/push and forcing an immediate outbox retry, so staff aren't stuck waiting for the 15-minute timer if they know connectivity is back.
  • Last synced timestamp — "Products updated 4 min ago" builds trust that the cache isn't stale.
  • Per-record status — any order/invoice created offline is visibly tagged "pending sync" until confirmed, never shown as identical to a normal completed sale.
