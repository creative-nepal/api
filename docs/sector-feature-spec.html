Feature specification

Mart · Medical · Restaurant — sector features

Detailed feature breakdown per sector plugin, plus the shared invoicing engine every sector depends on for sequential, non-missing invoices pushed to IRD's Central Billing Monitoring System (CBMS).

Overview

How this maps to the architecture

Every sector below plugs into the same core from the earlier architecture doc — Auth, Subscription/Entitlement, Billing engine. What differs per sector is the product schema, the order pipeline, and which roles exist. Restaurant differs the most: instead of staff creating every order, the customer initiates it.

Shared / all sectors

Invoicing engine & IRD (CBMS) compliance

This is not sector-specific — it lives in the core Billing engine and every sector's checkout flow calls into it. Nepal's IRD requires approved billing software to number invoices sequentially per fiscal year, never silently alter or delete an issued invoice, and report each sale to the Central Billing Monitoring System (CBMS) — so this is the part of the system that's least safe to get wrong.

01Gapless sequential numbering

One counter per business per fiscal year (Bikram Sambat), incremented atomically at invoice creation — never at cart/order creation, so abandoned carts can't burn a number.

02No hard deletes

An invoice is never deleted or edited in place. Corrections go through a credit note referencing the original — the master register always shows every number issued.

03Single-print + copy marking

First print is the original; every reprint auto-stamps "Copy of original" with a reprint counter, logged.

04Offline-safe CBMS sync

Invoices are created and printed even if IRD's endpoint is unreachable. A background worker retries a push queue until each invoice is acknowledged — never blocks checkout.

05PAN & VAT breakdown

Business PAN, buyer PAN (when applicable), taxable amount, and VAT (13%) computed and shown as separate fields on every invoice, not just a total.

06Full audit trail

Every state change on an invoice (created, printed, reprinted, credit-noted, synced, sync failed) is appended to an immutable audit log — required for both disputes and IRD inspection.

Numbering safety, concretely — this is the part that must never produce a gap or a duplicate

-- one row per business per fiscal year, updated inside the same DB transaction as invoice insert
invoice_counters
  business_id (fk), fiscal_year, last_number, UNIQUE(business_id, fiscal_year)

-- pseudocode, runs inside a single serializable transaction:
next_number = UPDATE invoice_counters
              SET last_number = last_number + 1
              WHERE business_id = :b AND fiscal_year = :fy
              RETURNING last_number
invoice.number = "{business.pan}-{fiscal_year}-{next_number}"

Why this matters: generating the number in application code (e.g. COUNT(*) + 1) races under concurrent checkouts and produces duplicates. The row-level lock from an atomic UPDATE ... RETURNING inside the invoice's own transaction is what guarantees no two orders ever get the same number and no number is skipped.

Mart

Checkout, order creation & billing

  1. Cashier scans barcode or searches product → added to cart with quantity (supports fractional quantity for weight/volume units, e.g. 0.5 kg).
  2. Cart validates stock availability live — can't oversell.
  3. Apply discount (item-level or bill-level, within manager-approved limits), select payment method (cash / card / wallet).
  4. On confirm: order is created, stock is decremented, and an invoice is generated in the same transaction — either all three succeed or none do.
  5. Invoice follows the shared numbering + CBMS push flow described above.

Atomicity matters here: stock deduction and invoice creation must be one transaction. A crash between "stock deducted" and "invoice created" is exactly how a mart ends up with inventory that doesn't match sales.

Mart

Analytics & alerts

Sales analytics

Daily/weekly/monthly revenue, best/worst-selling products, category-wise breakdown, cashier-wise sales.

Stock valuation

Current inventory value at cost vs at selling price — live snapshot for the owner.

Margin analysis

Profit per product/category using price - cost_price, surfaced alongside volume so low-margin best-sellers are visible.

Trend view

Compare this period vs last period — flags products trending down before they become a stock problem.

Alerts

  • Low stock — product falls below its low_stock_threshold.
  • Expiring soon — configurable window (e.g. 7/15/30 days out).
  • Expired stock — daily sweep flags anything past expiry_date still in stock; sale of an expired item is blocked at checkout, not just warned.
  • CBMS sync failed — an invoice sat in the retry queue past a threshold; ops needs to know before it becomes a compliance backlog.

Medical

Product & batch management

Same checkout/order/analytics skeleton as mart — but the product entity and stock model change enough that they can't share the same schema unmodified.

FieldNotes
name, generic_nameBrand and generic/composition name — pharmacists search by either
categorye.g. Analgesic, Antibiotic, Syrup, Device
manufacturerFor recalls and regulatory reporting
scheduleotc / prescription / controlled — drives what's required at checkout
unit_typestrip, bottle, vial, box, pcs — no barcode field; medical sale is stock lookup by name/batch, not scan
Stock is tracked per batch, not just per product:
batches[]batch_no, expiry_date, qty, cost_price — a product can have several active batches with different expiries

Why no barcode: unlike a mart, medical stock is managed at the batch level — the same product can have five batches with five different expiry dates on the shelf simultaneously. A single barcode per product would hide which batch is actually being sold, which is the opposite of what a pharmacy needs.

Medical

Sector-specific features

FEFO dispensing

Checkout auto-suggests the batch with the nearest expiry first (First-Expire-First-Out), overridable by the pharmacist.

Prescription attach

For schedule = prescription items, order requires an attached prescription (photo/scan) + prescribing doctor's name before checkout completes.

Controlled substance register

Sales of schedule = controlled items log buyer ID/details in a separate append-only register, as typically required for narcotics-class drugs.

Expired-batch hard block

A batch past expiry_date is automatically excluded from sale — not just flagged, actually unsellable at checkout.

Insurance claim linkage

Order can be tagged with an insurance provider + policy number; claim status (submitted/approved/rejected) tracked against the invoice.

Return / damage / expiry write-off

Separate stock-adjustment reason codes so "returned by customer," "damaged," and "expired write-off" are distinguishable in reports — different regulatory and accounting treatment.

Regulatory export

Batch-wise sales/stock report exportable in a format suited for drug authority inspection — extension of the same analytics engine mart uses, with batch and schedule columns added.

Medical

Roles

Ownerfull access Managerinventory, batches, staff Pharmacistonly role that can dispense prescription/controlled items

Why a distinct pharmacist role: checkout for a prescription or controlled item should be blocked unless the acting user holds the pharmacist role — a plain cashier role (fine for mart) isn't sufficient here.

Restaurant

Menu & QR ordering

EntityKey fields

Table-scoped session

Scanning a table's QR opens the menu with a short-lived session token bound to that table_id — no account needed, but every order from it is traceable to the table.

Live menu availability

Kitchen or manager can 86 (mark unavailable) an item instantly — customer menu reflects it immediately.

Modifiers

Size, spice level, add-ons/removals per item, priced individually where needed.

Multiple orders per table

A table can place several orders across a sitting (starters, then mains, then dessert) — all tracked and billed together at the end.

Restaurant

Kitchen & service (KOT)

  • Confirmed order auto-generates a KOT (kitchen order ticket) routed to a kitchen display screen or printer, grouped by station if needed (grill, drinks, dessert).
  • Chef updates status per item or per ticket: in_kitchen → preparing → ready.
  • Waiter gets notified when a ticket is ready, delivers it, marks served.
  • Kitchen never sees pricing/billing — chef role is scoped to KOT status only, keeping the kitchen display simple and fast.
Restaurant

Billing

  1. Waiter or cashier opens the table → sees all orders/KOTs placed against it during the sitting.
  2. Choose split by item or split by guest count if the table asks to divide the bill.
  3. Apply service charge (if applicable) + VAT.
  4. Generate invoice → same shared sequential numbering + CBMS push engine as mart/medical.
  5. Table status flips to billed, then empty once payment is confirmed, freeing it for the next QR session.
Restaurant

Analytics & alerts

Table turnover

Average time from seated to billed, per table and per day-part — the core lever for restaurant revenue.

Item performance

Best-selling items, modifier attach rate, items frequently 86'd (signals supply issues).

Waiter/kitchen performance

Average confirm time, average prep time, orders served per waiter per shift.

Peak-hour heatmap

Orders by hour/day for staffing decisions.

Alerts

  • Order stuck — no status change past a time threshold at any stage (placed/confirmed/preparing).
  • Table waiting for bill — status served too long without a bill request.
  • CBMS sync failed — same shared alert as mart/medical.
